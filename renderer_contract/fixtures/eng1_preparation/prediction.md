Prediction (written before the new native trace): the current three resource calls share one visit address and cell ID 0, so 2E3B0 should show a cache-key distinction: an initial path establishes per-visit prep state, while later visits with the same cell key reuse some transform state. The 384→320 result should be attributable to a specific native write in the bounded 2E3B0 span (or a helper it actually calls), not an output coordinate injected into the candidate. Falsifier: the detailed original trace for calls 2, 23, and 74 shows no read/branch keyed by the visit cell/cache fields, or shows the 384→320 write is produced by an unsupported callee/state source whose inputs cannot be bounded from the actual resource call. A falsifier ends the family at that exact PC/callee/owner; it does not justify synthesizing camera state or extending the function span. The source acceptance check is native-vs-C equality for callback sequence, widths, touched visit/matrix/config cells, depth and return under the same explicitly controlled case inputs, followed by the existing 481 emitter checks with C-derived prep.

Scope: three existing real archived MAP_PSX.BIN cases only (mesh 156/call 2, mesh 284/call 23, mesh 17/call 74); the finite frame/camera setup remains controlled. Asset and original PE bytes are read-only. This experiment does not claim live startup, recovery, whole-map behavior, or strict function equality.
