# Frame and ordering-table contract (PC originals)

## Scope and prediction

This receipt covers the original HERCULES host callbacks AC20/AC60, their ENG1/ENG3/TITLE copied-interface wrappers, the ENG1 double-frame dispatch tail, and TITLE's double-buffer order-table path. It reuses the already accepted `exe.frame_chain_write` proof and does not reconstruct the rasterizer call graph.

The pre-experiment prediction in `prediction.txt` was a pair of `0x1488` ENG1 views with `0x500` raw32 link cells at `+0x88`, slot rotation after submission, and an independently wrapped module path. The observed writer, allocation, call order, and toggles support it. The original TITLE wrapper call sites establish a distinct `0x1478` display-buffer stride and `+0x70` order-table offset. The prediction would have been falsified by a different count or stride, a toggle before submission, missing paired initialization, or wrapper bytes dispatching through a different slot/ABI.

The ENG3 shape was a follow-up investigation after the initial cross-module scan, so the original prediction did not pre-state ENG3 dimensions. Its result is reported as directly measured spans and remains static-only; a different allocation request, table count/offset, second-view displacement, or submit argument would falsify the measured ENG3 description.

## Host writer and traversal

`HERCULES.EXE` AC20 (`0xAC20..0xAC40`, 32 bytes; SHA-256 `f96f2d7aĂ˘â‚¬Â¦`) is the already accepted `FUNCTION_MATCH` in `recovery.json`, sourced from `src/pc/frame_chain_write.c`. Its physical contract is two caller-cleaned raw32 arguments: first slot address and count. It decrements the count, links each slot forward to the next four-byte slot while the signed remainder is positive, writes a final NULL unconditionally, clears EAX, and returns. A positive `0x500` call therefore writes `0x4ff` forward links and one NULL across `0x1400` bytes. The post-decrement signed branch means zero/negative inputs still write one NULL; parameter signedness in the original C declaration is not established.

`HERCULES.EXE` AC60 (`0xAC60..0xB2F0`, 1680 bytes; SHA-256 `f7724c04Ă˘â‚¬Â¦`) receives one raw32 pointer to the first order-table head cell. It loads the head and sets a cursor to `arg+4`. When the current head equals that cursor, it treats the value as the next-slot sentinel, dereferences that slot for the next bucket head, advances the cursor by four, and repeats; this naturally skips empty buckets. A nonempty primitive head differs from the cursor and is visited. Following a primitive's first DWORD to the cursor marks that bucket's tail only after that primitive has been visited; AC60 then loads the next bucket head and advances. The walk ends when the loaded head is NULL. AC60 has no explicit `0x500` count bound; the fixture's range, cycle, and visit-budget stops are decoder safeguards only.

The table cursor advances from low to high slot addresses. TITLE's observed emitter chooses `ot[0x500 - 2 - unknown_010]`, where `unknown_010` is the source's depth-like bucket input; no range or broader semantic meaning is inferred. Inserting a primitive stores the previous bucket head in its first DWORD and makes the new primitive the bucket head, so multiple primitives in one bucket are visited newest-first. AC60's internal rasterizer branches remain outside this receipt. At its tail, the original condition on host byte `BA01FC` gates calls `70C0(0xFF)`, `7140()`, and `6620()`; `BD80()` follows on both paths. A replacement bypass must retain this observed call order and branch. The meanings and full side effects of those helpers are not expanded here.

AC20 and AC60 are distinct callbacks: the statically observed host interface source table at RVA `0x361B8` maps offset `0x144` / slot 81 to VA `0x40AC20`, and offset `0x164` / slot 89 to VA `0x40AC60`. ENG1, ENG3, and TITLE each copy 250 DWORDs into module-local interface tables. This proves the static file binding; runtime writes through computed aliases remain possible and were not ruled out.

## Module wrappers and frame order

Each module has its own target-byte wrapper pair. The `+0x144` wrapper loads and pushes `(first, count)`, calls its copied slot 81, caller-cleans eight bytes, then returns; AC20 supplies EAX zero. The `+0x164` wrapper pushes one pointer through slot 89, caller-cleans four bytes, then returns the physical EAX left by the callback. AC60 has no explicit return contract, and the measured ENG1/TITLE call sites ignore EAX. The spans and raw hashes are in `audit.json`.

| Module | `+0x144` chain initializer | `+0x164` order-table submission | Proof status |
|---|---:|---:|---|
| ENG1 | `0x2C600`, 32 bytes | `0x2C620`, 16 bytes | Both wrapper contracts statically audited. `2C620` is `CODEGEN_SIMILAR`; no separate recovery entry was found for `2C600`. |
| ENG3 | `0x1FC10`, 32 bytes | `0x1FC30`, 16 bytes | Both are `CODEGEN_SIMILAR`; relocation-masked equivalence is diagnostic. |
| TITLE | `0xC690`, 32 bytes | `0xC6B0`, 16 bytes | Both are `CODEGEN_SIMILAR`; relocation-masked equivalence is diagnostic. |

ENG1 requests one `0x2910`-byte frame block through owner cell `0x71EC8`, then initializes chains at owner `+0x88` and `+0x1510` with count `0x500`. Each link region is `0x1400` bytes; the second ends exactly at `0x2910`. Thus the minimum observed view stride is `0x1488` and the two views fill the request. The common setup also runs after a nonzero completion-gate result and reinitializes both chains. Only the prefix and chain locations are established; this does not prove a complete original C type or other field meanings.

ENG3 has a separate measured envelope. `ENG3.DLL` RVA `0x1A330` requests `0x4110` bytes with alignment/argument `0x10` through wrapper `0x1FA50`, passing the address of global cell `0x1004144C`. RVA `0x1A560` copies that current-cell value into cell `0x10041448`, then initializes raw32 chains at current `+0x88` and current `+0x2110`, each with count `0x800`. Each table spans `0x2000` bytes, so `0x2110 == 0x2088 + 0x88` and the two observed views are separated by `0x2088`; their pair fills the `0x4110` request. The two wrapper calls and allocation request are direct original observations, while interpreting each interval as a view is a byte-range description, not a recovered complete C type.

ENG3 teardown at `0x1A460` passes the current-cell value to wrapper `0x1F960` after releasing earlier objects; it does not show a null write to that current cell in the inspected span. The setup helper initializes both `0x800` chains and later conditionally writes the other global to the current value plus `0x2088`. During the lifecycle, the active-view reset at `0xA700` initializes the other-cell value plus `0x88` through `0x1FC10` with count `0x800`; the lifecycle calls this helper at `0x1ADC9` before its frame callbacks. At `0x1AEAF` it passes the other-cell value plus `0x88` through `0x1FC30` to copied slot `+0x164`. The observed order around submission is: call `0x1FB80(other-cell value)`; conditionally call `0x8050` when context byte `+4` is zero; call `0xA1D0` and `0xAA70`; submit the order table; call `0xB512`; call `0x20030(context+0x34)`; compare the two global cells and conditionally store current plus `0x2088` to the other cell; increment context tick; call completion gate `0xB059` and branch back to setup on nonzero. These are raw call/write facts, not meanings assigned to the helpers. Since callback bodies and runtime alias writes are outside this bounded audit, the cells are named by location rather than asserting stable semantic roles, and no per-frame pixel/presentation result is claimed.

On each ENG1 dispatch iteration, the observed order is: call `2C570(current)`; optional `2CB0()` when context byte 4 is zero; `50D0()`; `58B0()`; submit `current+0x88` through `2C620` to AC60; call `666B()`; call `2CA40(context+0x34)`; toggle current between base and base `+0x1488`; increment context tick at `+0x38`; then call `60F9()`. A nonzero `60F9` result jumps to common restart/setup before the next iteration. The toggle follows submission and all preceding callbacks. The owner/current cells are reloaded as shown by the original; don't retain a pointer across callbacks or substitute an allocation guard.

TITLE allocates `0x28F0` bytes and views buffers `0x1478` apart. Each observed TITLE order table begins at buffer `+0x70` and has `0x500` raw32 slots; the final eight bytes of the `0x1478` view are not assigned meaning here. `title_1d590` initializes both tables through `0xC690` with count `0x500`, sets current to base for setup, initializes the paired draw/display environments, then toggles current to the second view. Each title frame's common path calls `0x04660` before drawing; that routine clears the current OT through `0xC690(current+0x70, 0x500)` and selects the corresponding half of the title primitive pool. The path then runs its title callbacks and `0x02B70`, calls `0C960(0x80)`, submits `current+0x70` through `0xC6B0` to AC60, toggles current between the two views, and increments tick. The return from TITLE `0xC6B0` is ignored at this call site. Do not assume the first submitted buffer is the base: setup's final toggle selects the second view.

These sequences state only observed calls and writes. They do not establish pixel output, a GPU implementation, a whole-module layout, or a renderer replacement. The host's table and callback side effects remain part of the required native contract if these routes are bypassed.

## Fixed-width contract and fixture

`candidates/renderer_frame/frame_contract_draft.h` is a reusable measured-layout draft, not an asserted original structure declaration. It includes the fixed-width types from `renderer_packet_width.h`; ENG1, ENG3, and TITLE have separate descriptors and no common original native aggregate is claimed. `frame_chain_walker.c/.h` expose a bounded raw32 API with caller-supplied resolver and visit guard. Raw32 values are decoded bytewise as little-endian and never converted to host pointers. The AC60 model takes an explicit slot count solely as a decoder boundary (AC60 itself has no explicit count); a one-past final sentinel returns `FRAME_WALK_RANGE_ERROR` before resolver lookup. Other range, cycle, overflow, and visit-budget checks are fixture-safety guards, not native AC60 behavior. The fixture calls accepted `src/pc/frame_chain_write.c` in the historical x86 run and uses synthetic fixed-width initialization in the x64 host run. It checks ENG1/ENG3 pairs, TITLE tables, depth indexing, newest-first prepend order, AC60 sentinel skipping, terminal NULL, invalid final links, mapped one-past rejection, cycles, and decoder budgets.

Both the pinned VC5 x86 compile/link/run and an x86_64 GCC C89 compile/run passed 36 checks with zero failures. These validate the fixed-width layouts and bounded synthetic traversal only; they are not a native-versus-original renderer differential and make no pixel claim. Exact compiler, linker, commands, and output hashes are recorded in `evidence.json`; `run_fixture.ps1` and `run_portable_tests.ps1` reproduce the runs. `audit_originals.py` checks baseline original hashes, extracts the audited PC spans (including the ENG3 allocation, release, setup, and lifecycle spans), records SHA-256 values and disassembly, hashes its evidence inputs, and writes `audit.json` plus `disassembly.txt` without modifying originals.

## Proof boundary and open points

- AC20 is the only function in this frame receipt with strict `FUNCTION_MATCH` status. Its complete source identity is limited to the accepted candidate; original full frame types, source translation unit, and ownership are not inferred.
- AC60 traversal and call/branch order are static observations from its hash-pinned original span, not a reconstructed or exact-equality C function. No full rasterizer call graph is duplicated here.
- ENG3/TITLE wrappers and TITLE frame/setup functions remain `CODEGEN_SIMILAR`; raw target bytes are independently hashed, but diagnostic relocation-normalized similarity is not function equality. ENG1 wrappers are documented at target-byte scope as shown above. ENG3 envelope observations are static original-span facts, not exact-equality recovered C functions.
- Static copied-table cells identify the default callback targets. Runtime alias mutation is not excluded. Allocation owner/current lifetime follows the observed live-cell reload and toggle protocol; no ownership beyond those accesses is asserted.
- The 32-bit fixture's linked-list cycle, range, and visit-limit checks only prevent unsafe decoding. AC60 itself is observed to terminate on NULL and does not use those synthetic guards.
