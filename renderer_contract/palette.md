# Palette and indexed-table lifetime

The original host has a bounded startup generator for the shade, blend, and procedural CLUT data, plus later resource-driven palette/table updates. Those buffers alias one another, so the observed extents must be treated as one writer map rather than independent allocations. Retaining the original palette, DirectDraw, surface, lock, clear, and present services while redirecting selected engine source-table entries is the smallest evidenced bootstrap boundary.

`0x72A0` initializes GDI DIB/palette state, calls `0x6FF0`, calls `0x71A0`, then calls the imported `DirectDrawCreate` thunk at `0x7426`; presentation evidence places this before the first engine source-table copy. The PE `.data` virtual tail contains the mode and graphics globals and starts zero-filled when `VirtualSize` exceeds `SizeOfRawData` ([Microsoft PE Format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)). Therefore, the first `0x71A0` call to `0x69A0(1)` is before DirectDraw mode is active and takes the GDI/DIB branch.

`0x71A0` writes shade bytes `[0x91C488,0x92C488)` as `min(255,(row*column)>>7)` and four 64-KiB blend tables `[0x92E3D0,0x96E3D0)`. Their formulas by selector are average, saturated sum, `max(column-row,0)`, and `min(floor(row/2)+column,255)`. It then writes 32 procedural CLUT rows `[0x92C490,0x92E490)`, each the byte ramp `0..255`. CLUT row 32 begins at `0x92E390`, so its final 192 bytes overwrite selector-0 row 0 columns 0..191 at `0x92E3D0..0x92E48F` with `64..255`; columns 192..255 retain the average results. The CLUT writer does not write the mode byte `0x92C488` or the seven following bytes.

The independent bounded CPU fixture `test_original_71a0_palette_builder.py` maps the pinned PE unchanged in Unicorn, executes original `0x71A0` plus `0x6780`, and stops at `0x728D`, before the `0x69A0` call at `0x728F`. It used 2,356,875 instructions of a 20,000,000 budget, recorded 335,872 table write events over 335,680 unique bytes, and saw exactly 256 entries into helper `0x6780`. Every table byte matched independently computed formulas plus the CLUT overlap; the original `.text`, `.data` outside allowed tables, disk EXE, and guard canaries remained unchanged. At selector 0 / source 0 / destination `0x3c`, the formula writer stored 30 and the later CLUT writer stored 124; column 191 ends at 255 and column 192 retains 96. Full final table hashes and the exact run receipt are in [native_palette_builder.json](evidence/native_palette_builder.json). This confirms the startup byte order only; it does not execute the presentation call or initialize Windows/DirectDraw.

`0x68C0` is a separate resource update called at `0x59E5`, followed by `0x69A0(1)` at `0x59EF`. It writes 256 RGB triplets through `0x6780`, then requests blocks of `0x40000` bytes at `0x92E3D0`, `0x10000` at `0x91C488`, and `0x1F00` at `0x92C490` (31 CLUT rows from row 1). Its CLUT block ends at `0x92E390`, 64 bytes before the blend base. It clears `0x96E3E0` and compares rows 2..32 with their predecessors. Row 32 is not loaded by this payload and overlaps the first 192 bytes of selector-0 row 0 if that blend table was already generated. The global ordering of this loader relative to `0x71A0` is unresolved.

The palette is held at `0x96E3F8` as 256 `PALETTEENTRY` values (RGB and flags=4), mirrored in the RGBQUAD block behind `0x96E3F4` for a 320×−240, 8-bpp BI_RGB DIB. `0x6780(index,R,G,B)` updates both formats; indices 0 and 255 are forced to grayscale. `0x6850` searches the 256 GDI entries by squared RGB distance and retains the lower-index tie. `0x72A0` allocates the LOGPALETTE and BITMAPINFO blocks and creates a GDI HPALETTE; shutdown `0x74C0` restores the prior selected palette, deletes the HPALETTE, and frees/nulls the buffers.

After DirectDraw setup, mode transition `0x6BB0` calls `0x6A60`, which releases old surfaces/palette, creates the primary and attached surfaces at `0x96E3E8`/`0x96E3EC`, creates an `IDirectDrawPalette` at `0x96E3F0` with 256 black entries, and attaches it to the primary surface. `0x69A0` unlocks, asks `0x6EE0` to clear RGB(0,0,0), and presents. In DirectDraw mode it updates 256 palette entries through `IDirectDrawPalette::SetEntries`; in GDI mode it updates the HPALETTE and `0x6700` selects/realizes it before presenting. `0x6700` also handles `WM_PALETTECHANGED` (`0x311`). Surface lost/restore details remain in the separate `directdraw_surface_control_2026_10_11` evidence.

`0x6EE0` is required for color-clear behavior. When unlocked, it translates RGB through `0x6850`, fills the whole DirectDraw surface using `Blt` with `DDBLT_COLORFILL|DDBLT_WAIT`, or fills 320×240 indexed bytes in the DIB; it records the buffer and pitch and marks `0x43A590` dirty. If already locked, it skips the fill. The engine packet path at `0xAC60` calls `0x6EE0` at `0xAC8A` when its `0x96E698` color-change flag is set. The host also directly calls `0x70C0` from `0xB2D0` and `0xA710` from `0xA675`; these are outside the engine source table. A renderer bypass must preserve those host paths and their state effects.

The startup-builder prediction is confirmed for its bounded write family and falsifies the claim that selector-0 row 0 is independently allocated or untouched by CLUT construction. The `0x68C0` versus `0x71A0` lifetime ordering remains unproved. Smallest viable bootstrap: preserve the original HWND and DirectDraw/GDI services through initialization, surfaces, palette updates, lock/unlock, clear, and presentation; redirect only selected engine source-table callbacks after the host table is initialized. Do not assume raster submission is the presentation boundary or that an installed proxy DLL is selected by local loader search order; deployment resolution remains untested.
